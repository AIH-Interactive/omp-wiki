# OmniMorph Wiki 编辑规范

本文件面向所有参与 Wiki 编写与翻译的人（包括 AI 助手）。目标是让页面**准确、统一、可照着做**，并且全站保持简体中文。

---

## 1. 语言规则

- 除代码、API 标识符、枚举值、文件名、JSON 字段、错误码外，正文一律使用简体中文。
- 英文专有名词首次出现时写成“中文（English）”，后文使用中文或保留通用英文名。
- 中文与英文、数字之间加一个空格，例如：`使用 8 个槽位`、`调用 ysm_model 接口`。
- 使用中文标点（，。；：！？），不使用英文逗号/句号代替。
- 不使用机器翻译腔；句子尽量短，一步一个动作。
- 不用“显然”“简单地”“众所周知”等主观词；不承诺未经验证的行为。

## 3. 页面结构

### 3.1 功能指南

1. 标题下注明状态与适用版本。
2. `## 这是什么`：一句话说明用途。
3. `## 前置条件`：需要先完成什么。
4. `## 操作步骤`：编号列表，每步一个动作。
5. `## 结果`：操作后应看到什么。
6. `## 示例`：Lua / JSON / 截图（截图缺失时注明“待补”）。
7. `## 限制与错误`：权限、预算、常见失败原因。
8. `## 常见问题`、`## 相关页面`。

### 3.2 API 参考

- 每个类型一页，开头说明“如何获得该对象”和“可用范围”。
- 每个方法使用 `### <code>method(args)</code> \{#method}` 作为标题。
- 依次给出：别名、说明、参数表、返回值表、示例、注意事项。
- 方法名、参数名、枚举值保持英文，说明用中文。
- 示例至少一个，尽量可直接运行。

### 3.3 教程

- 开头写“你将完成”“准备”。
- 步骤编号连续，每步说明“做什么/为什么”。
- 最后给完整代码与排查清单。

## 4. 代码与标识符

- Lua 使用 4 空格缩进；运算符两侧留空格；一行一个概念。
- 代码块语言标记：`lua`、`json`、`bash`、`powershell`、`text`。
- 不翻译代码中的标识符、字符串键、枚举值、路径。
- 代码注释可以中文，但不要改动代码逻辑。
- JSON 示例必须是合法 JSON，不能带注释或尾逗号。

## 5. 链接与图片

- 内部链接使用绝对文档路径，例如 `/globals/Player/Player`。
- 不链接尚不存在的页面；先创建占位页或暂时移除链接。
- 图片必须有中文 `alt`。
- 旧英文界面截图若与当前界面不符，标注“旧版界面示意”。
- 新功能截图统一标注“截图待补（MANUAL/PENDING）”，不得用合成图冒充。

## 6. 提示框

| 类型 | 用途 |
| --- | --- |
| `:::note` | 补充说明 |
| `:::tip` | 技巧 |
| `:::info` | 信息 |
| `:::caution` | 注意 |
| `:::warning` | 警告 |
| `:::danger` | 危险操作 |

## 7. 状态标记

在页面开头使用以下标记之一：

- **稳定**：当前版本可用，行为已由源码/验收记录支持。
- **预览**：功能存在，但界面或行为可能变化。
- **依赖后端**：需要兼容后端与相应能力开关。
- **2.0 占位**：界面存在但业务未实现，不得描述为可用。

## 8. 提交前检查

1. 正文是否全中文（代码/标识符除外）。
2. 术语是否符合术语表。
3. 内部链接、图片、锚点是否有效。
4. 示例是否与 `omp-ref` 当前源码一致。
5. 是否误把未验证功能写成“已完成”。
6. 是否运行 `pnpm build` 并通过。

## 9. 常用中文句式

- “本页介绍……”
- “要使用此功能，需要先……”
- “在衣柜中选择……，然后点击……”
- “如果失败，请检查……”
- “该值受……限制。”
- “此功能依赖后端能力，服务器未开启时不会显示。”

避免：

- “用户可以……”
- “这个功能非常强大……”
- “只需简单几步……”
- “众所周知……”
